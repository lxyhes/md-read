# 墨阅知识库升级设计

第一版让知识库在「本次资料」里同时按关键词和语义找原文，并继续使用现有的引用跳转。适用场景包括中文换说法、中英术语混用，以及精确查找型号、数值和代码符号。桌面端先做，默认沿用当前关键词检索，用户可以开启本地语义检索。

## 1. 用户怎么用

| 场景 | 墨阅的行为 |
| --- | --- |
| 首次开启 | 在「设置 → 阅读偏好 → AI 能力」增加「本地语义检索」。说明需要本机 Ollama 和 `qwen3-embedding:0.6b`，提供检测与可复制的安装命令 `ollama pull qwen3-embedding:0.6b`。生成回答的模型仍在原设置中选。 |
| 打开知识库 | 在「本次资料」下显示短状态，例如「语义索引 12/20 篇，全部资料可用关键词检索」。进入知识库后优先为本次资料后台建索引，切换资料时调整队列。 |
| 提问 | 搜索范围取自提交瞬间的「本次资料」。索引覆盖一部分时，已就绪文档可以参与语义召回，全部所选文档仍可参与关键词召回。关闭 AI 生成时也能看原文结果。 |
| Ollama 暂时不可用 | 当轮自动用关键词检索，在回答或原文结果旁标明「本轮使用关键词检索」。浏览器预览和关闭开关时继续走原有入口。 |
| 点击引用 | 跳到当前文档中对应的段落或阅读区域。文档修改或移除后，历史对话仍可查看当时的摘录，继续沿用已有的引用状态。 |

当前问答入口和范围由 `App.vue` 管理，历史引用由 `knowledgeConversations.ts` 管理。第一版使用现有知识库布局。`Ctrl+K` 全文搜索仍是独立入口。 [问答入口](../src/App.vue#L3192) · [引用状态](../src/knowledgeConversations.ts#L201)

## 2. 一次提问怎样找到证据

```text
本次资料 + 当前问题（追问沿用现有上下文处理）
  ├─ 关键词召回：沿用现有中文切分、精确短语与标题加权
  └─ 本地向量召回：搜索已就绪且版本匹配的资料
       ↓ 按名次融合 → 去重 → 选最多 8 条原文
       ↓ 点击可跳转的原文摘录 + 同小节上下文
  原文结果，或交给现有 AI 问答生成带引用的回答
```

1. **按 Markdown 结构建索引。** 从 `ReaderRegion` 和标题深度取得标题路径与正文。合并同一小节的短段落，保留每段的 `regionId`。表格、代码块独立处理。必须拆长表格时重复表头，必须拆长代码时按行拆，继续映射到原阅读区域。起始目标是每块约 400–800 中文字符，允许完整保留较短的表格和代码块。文档输入带标题路径，查询输入按 Qwen 模型卡带检索任务指令。以评测结果调整大小。 [阅读区域类型](../src/types.ts) · [HiChunk 研究](https://aclanthology.org/2026.acl-long.1372/) · [Qwen 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)
2. **候选比最终引用多。** 每路先取约 24 条，按倒数排名融合（RRF），避免直接相加两套尺度不同的分数。复用正文精确匹配信号，让型号、数字和代码标识符命中有机会保住靠前位置；按证据去重，并在最终 8 条里兼顾同一小节的必要上下文和跨文档覆盖。现有检索的文档配额在合并后再应用，候选阶段先保留可能有用的段落。24 和 8 是原型起点。 [墨阅关键词实现](../src/knowledgeSearch.ts#L219) · [QMD 对照方案](https://github.com/tobi/qmd#benchmarking)
3. **检索块用于找位置，引用落到可见原文。** 选中合并块后，定位一个最相关的 `ReaderRegion`；证据确实分散在多个区域时，分别给出引用。摘要类问题保留现有的章节覆盖思路，并把本轮最好证据和上下文打包；让原文摘录与点击位置对应。`KnowledgeCitation` 沿用现有字段。 [引用构造](../src/knowledgeConversations.ts#L120)

## 3. 索引怎么存、怎么更新

| 位置 | 设计 |
| --- | --- |
| Tauri 与 Ollama | 在现有 Rust 请求层添加固定回环地址的 `/api/embed` 调用。首版使用 `127.0.0.1:11434` 和固定模型，批量提交正文。关闭代理与重定向，校验返回条数、维度和数值，给查询与后台批次分别设置超时。查询等待超过原型预算 2 秒就走关键词，建索引继续在后台进行。 [现有 Tauri 请求](../src-tauri/src/lib.rs#L488) · [Ollama Embedding API](https://docs.ollama.com/api/embed) |
| SQLite | 在现有 `moyue.db` 增加可重建缓存。一篇文档、一个内容版本的块定位信息与向量作为一条缓存记录一次写入，完整成功后才标记就绪。键包含文档 ID、`sourceHash`、模型 digest、切块版本和向量维度；模型标签相同但 digest 变化也要失效。原型用归一化 Float32 向量做余弦扫描，基于规模与延迟结果决定是否换索引引擎。 [现有数据库](../src/persistence.ts#L101) · [Ollama 模型 digest](https://docs.ollama.com/api/tags) |
| 文件变更 | 索引取自当前 `store.documents` 的已保存快照。应用内保存或已监听文件重载后，旧版本立即退出召回，后台重算该文档。改名后的 ID 按现有路径规则生成，缓存按新 ID 重建。移出本轮范围立即排除；删除库中文档时清理其向量，历史引用仍保留。后台每次处理一批，同一文档版本合并重复任务，写入前复核文档和模型版本，查询出结果时再次核对范围和版本。 [文档保存与改名](../src/stores/reader.ts#L145) · [解析与 ID](../src/parser.ts#L177) |
| 外部编辑 | 现有文件监听仅覆盖打开的标签。首版为知识库增加「刷新资料」动作，对本次资料中有本机原始路径的文件重新读取并复用现有重载逻辑。草稿冲突时保留快照并显示状态；确认磁盘文件已删除时，标记来源不可用并排除出本次检索。临时 I/O 失败和只有导入快照的来源显示「使用已导入版本」。 [现有监听范围](../src/App.vue#L4928) |
| 数据流 | 建索引只向本机 Ollama 发送已选文档内容。若回答模型配置的是远程服务，生成阶段仍会发送本轮入选片段及现有对话上下文；设置项旁标明实际去向。本地模型生成失败时，保留本轮原文结果供核对和重试。 |

## 4. 分三批交付

| 次序 | 交付内容 | 可以看到的变化 |
| --- | --- | --- |
| 第一批 | 段落级评测基线、Markdown 切块、本地向量缓存、混合召回、原文引用、索引状态和关键词回退。 | 同义表达能找到原文，重新打开墨阅可复用已经完成的索引。 |
| 第二批 | 在同一套题上比较「混合检索」与「混合检索加重排」，用重排处理少量候选。对低证据题展示原文或提示资料不足，逐项核对回答与引用。 | 相似小节多时更容易找到正确条件，资料里无答案时更少给出无支持的结论。 |
| 第三批 | 根据真实题集选下一项。如果对比题常漏证据，分最多 3 个子查询，再做一次汇总；如果主要资料在 PDF 或扫描件里，先做带原始页码的导入。 | 可以按证据比较多份资料，或从答案跳回 PDF 原页。 [分步检索研究](https://arxiv.org/abs/2605.05538) · [Docling 文档解析](https://github.com/docling-project/docling) |

## 5. 第一批验收

1. **建立基线。** 从现有 8 道文件级题开始，补到约 30 道含标准证据的题。覆盖中文改写、中英术语、代码标识符与数字、多份资料对比，以及资料中无答案。每题标出文件、小节和一段原文；跨文档题标出全部必要证据。 [现有评测](../src/knowledgeSearch.evaluation.test.ts)
2. **看正确段落进入前 8 的情况。** 同一语料比较纯关键词与混合检索。原型目标是中文改写题的证据召回率提升至少 10 个百分点，精确匹配题的首条命中数保持基线；小样本同时报告题数。生成测试单列引用支持率和无证据题误答数。检索效果与回答效果分别记录。
3. **验证资料范围与文件生命周期。** 对浏览器预览、无 Ollama、半索引、改名、编辑、关闭重开、删除、改选资料和模型更新各走一遍。范围和版本不匹配的块进入回答次数必须为零。验证历史摘录可查看，有效引用可跳转。
4. **在真实机器上量速度。** 记录首次建库时间和大小、冷启动与热启动的检索延迟，以及关键词回退耗时。把生成等待单列。2 秒是当轮语义查询的初始回退预算；全量扫描是否需要换实现，以目标机器和资料规模的实测为准。
